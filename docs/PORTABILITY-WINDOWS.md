# Portability to Windows (x86_64; arm64 later): design and list of changes

Status: **design, 2026-10-13** (DECISIONS D-134), amended the same day by D-135: the control endpoint is a named pipe,
not AF_UNIX. **The first W1 items are built** (2026-10-13): §2.0 says what was done and where it differs from the §2
table. Work goes in phases W0…W5 (D-134); phase W0 runs in
`.github/workflows/windows.yml`. SPEC §16 "Platforms v1" names Windows next to macOS and Linux. Targets: Windows 10 22H2
and Windows 11, x86_64 (MSVC); arm64 (`aarch64-pc-windows-msvc`) after x86_64 works. The WSL2 route (the Linux build,
the window through WSLg) stays the way to run Antenna on Windows until this port ships; it is not native (no keyboard
layout switching in WSLg, a frozen window were reported), which is why this port exists.

This document follows `docs/PORTABILITY.md` (the macOS port, M-1…M-18): every Linux- or macOS-specific piece, the
Windows API that replaces it, the option chosen, and what only a run on Windows can confirm. Items are **WP-1…WP-37**
(Windows portability), so they do not collide with the phases **W0…W5**.

## 0. Scope and how the facts were checked

- Code as of `main` at `95ba2e7`. Nothing was built for Windows here (no MSVC, no Windows SDK, no Flutter for Windows
  on the Linux build server).
- Crate facts were read in the sources of the versions in `Cargo.lock` (`~/.cargo/registry`): `tokio 1.53.1`, `mio
  1.2.3`, `rustix 1.1.5`, `aws-lc-sys 0.45.0`, `openssl-src 300.6.1+3.6.3`, `libsqlite3-sys 0.38.2`, `ring 0.17.14`.
  Dart facts in the Dart SDK sources and `CHANGELOG.md`; Flutter facts in `flutter_tools` at the tag `3.47.6`; runner
  facts in `actions/runner-images` (the Windows Server 2025 readmes of 2026-09-25 and 2026-10-04); Windows facts in
  Microsoft's documentation and the other primary sources listed at the end.
- **"To check"** marks what only Windows can confirm. Each one becomes a `FACT …` line printed by a test in
  `windows.yml` (the same practice as the macOS `core` job, D-P-14) or an item of the hands-on check on the test PC.
  Nothing marked "to check" is relied on for security until its FACT line is in a green run.

How much code assumes unix (counted 2026-10-13 with `grep` over `crates/*/src`; sites of `std::os::unix`, `rustix::`,
`libc::`, `UnixStream`/`UnixListener`):

| Crate | Sites | Where most of them are |
| --- | --- | --- |
| `antenna-proto` | 0 | portable (the data folder lookup in `local.rs` needs a Windows branch, WP-3) |
| `antenna-core` | ≈ 140 | `sandbox/` (supervisor, proxy, linux, macos), `control.rs`, `procinfo.rs`, `files.rs`, `agent_stop.rs`, `local/` |
| `antenna-files` | ≈ 160 | `sandbox_linux.rs` (95), `accept.rs` (40), `sandbox_macos.rs`, `quarantine.rs` |
| `antenna-cli` | ≈ 40 | `client.rs`, `main.rs`, `session/` (tmux), `setup.rs` |
| `antennad` | ≈ 16 | `main.rs` (umask, harden, signals), `handover.rs` (D-103) |

`rustix` is a plain dependency of five crates, but on Windows it has only its `net` and `event` parts: every
`rustix::process`, `rustix::fs` and `rustix::termios` call is a compile error there. `landlock` and `seccompiler` are
already under `cfg(target_os = "linux")`, `libc` in `antenna-sys` under `cfg(unix)`.

## 1. Summary

**Will not build (W0):** every crate but `antenna-proto`, `antenna-release` and `antenna-sys` (which is empty on
Windows), on `rustix::process`/`fs`/`termios`, `std::os::unix`, `tokio::net::UnixListener`/`UnixStream` (tokio has no
AF_UNIX on Windows, WP-5) and `tokio::signal::unix`. The C dependencies are expected to build on MSVC with NASM, a
native Perl and protoc (§3); the first `windows.yml` run confirms it.

**Will build after W0 with honest refusals, then work in W1:** the daemon and the CLI over the control pipe (D-135),
the owner commands with the password, links, pairing, messages, history, the MCP server for AI apps and agent CLIs,
which come by their token alone: D-135 offers no D-28 binding on Windows (WP-6…WP-10).

**Held, failing closed, until W3:** the file check worker (no confirmed isolation, so the verdict is `failed` and only
the owner's keep-anyway saves a file, as on any OS without isolation), and everything the daemon runs in the agent
sandbox: wake, resident agents, team workers and checks, the built-in local model runtime (`sandbox_unavailable` with
the reason).

**Parity of protections after the port:**

| Protection | Linux | macOS | Windows (this design) | Remainder on Windows |
| --- | --- | --- | --- | --- |
| Only the owner's user reaches the socket | `0600`, `SO_PEERCRED` uid | `0600`, `getpeereid` | a named pipe made as the first instance, with a protected DACL for the user alone; each client's token read by impersonating it at identification level: the user's SID, medium integrity or above, not an AppContainer, not restricted (WP-4, WP-5, WP-6; D-135) | a process of the user can make a further instance of the name, as it can replace the socket file on unix: clients check the pipe's owner and its server process before they send anything |
| Client PID | `SO_PEERCRED` | audit token (`pidversion`) | `GetNamedPipeClientProcessId`: the client's word (Project Zero, 2019), so it only restricts (D-135) | no D-28 binding on Windows: agents come by their token alone |
| PID reuse between connect and reading | open (D-41) | closed (`pidversion`) | the process is opened by PID and held while its creation time is read; a `held` session is bound to PID and creation time | the PID itself is the client's word (above) |
| Process chain | `/proc/<pid>/stat` | `proc_pidinfo` | `NtQueryInformationProcess` (parent PID), `GetProcessTimes` (creation time); a parent younger than its child is a reused PID and ends the chain (WP-7) | Windows does not re-parent orphans: the chain of a process whose parent exited ends there |
| A process can choose its parent | no | no | **yes**: `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` with `PROCESS_CREATE_PROCESS` on any process of the same user (WP-9) | the tree only restricts on Windows: no token-less agent by tree, a token-less process inside an agent's tree is refused |
| Owner session in a terminal | `tty` + `sid` + leader | the same | **none**: a console can be joined (`AttachConsole`) and a parent chosen, so neither identifies a terminal; the window's `held` session, and in a terminal one session held for each command, after its password (WP-10); Windows Hello later (W5) | the CLI asks more often than on Linux and macOS |
| Core dumps, memory reading | dumpable=0 | `RLIMIT_CORE=0`, `PT_DENY_ATTACH`, hardened runtime | WER excluded per user; the process DACL denies memory access to other processes of the user, with an `OWNER RIGHTS` entry so they cannot rewrite it (WP-11) | an elevated process with `SeDebugPrivilege` reads anything (as root does on Linux) |
| Inherited descriptors | `close_range` in the child (D-61) | `fcntl` walk | an explicit handle list (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) for every child the daemon starts (WP-12) | — |
| File check sandbox | Landlock + seccomp + rlimits | Seatbelt + watchdog | AppContainer (LPAC) + job object (one process, memory, CPU time, UI limits) + mitigation policies at creation (WP-19), experimental | kernel-enforced memory limit (better than the macOS watchdog); to check that the worker's dependencies load under LPAC |
| Agent sandbox | bwrap + Landlock + seccomp | Seatbelt | AppContainer + job, per-run file ACEs; the proxy bridge to be proven (WP-20), experimental | loopback inside an AppContainer and AF_UNIX from one are not documented: fail closed until the probes pass |
| Received file flag | — | `com.apple.quarantine` | `Zone.Identifier` stream with `ZoneId=3` (Mark of the Web), WP-21 | — |
| DB durability | `fsync` | `F_FULLFSYNC` | `FlushFileBuffers` (what SQLite already calls): nothing to add (WP-23) | — |

## 4. Tests

**New, Windows only (each prints `FACT …` with `--nocapture` in `windows.yml`):**
1. AF_UNIX: bind, connect, the peer PID ioctl equals the child's PID; a socket handed to another process with
   `WSADuplicateSocket` still reports the connecting process; a non-ASCII data folder path binds and connects (WP-3,
   WP-5, WP-6).
2. A client created after the accept, with a reused PID, is refused (simulated by checking a process whose creation time
   is later than a given accept time) (WP-6).
3. `procinfo`: own chain; the parent's creation time precedes the child's; a dead parent ends the chain; which queries
   succeed on an elevated and on a protected ancestor (WP-7).
4. Parent spoofing: a helper starts a child with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` = a bound host; the child's
   token-less connection is refused and is never that agent (WP-9). Negative control: with the Linux rule (forced role)
   the test fails.
5. Process hardening: another process of the user cannot open the daemon with `PROCESS_VM_READ` or `WRITE_DAC` (WP-11).
   Negative control: without the DACL it can.
6. The data folder DACL: only the user and `SYSTEM`; a folder with an extra entry makes the daemon refuse to start
   (WP-4).
7. Sandboxes (W3): the worker's probes from inside; a memory bomb stopped by the job; loopback inside one AppContainer;
   AF_UNIX from an AppContainer; a `node`/`git` command inside the agent sandbox (WP-19, WP-20).

**Portable as is** (expected green in W0): `antenna-proto`, `antenna-release`, the unit tests of `antenna-files` that do
not start the worker (`names`, `crypt`, `detect`, `inspect`, `cdr`, `secrets`, `kinds`), the unit tests of
`antenna-core` that do not touch processes or sockets.

## 5. Pitfalls found while designing

- `windows-latest` moved to Visual Studio 2026: anything that pins a Visual Studio generator name must follow it
  (`flutter_tools` 3.47.6 does: `Visual Studio 18 2026`).
- tokio has named pipes but no AF_UNIX on Windows; dart:io has AF_UNIX on Windows (Dart 3.11, 2026-02-11) but no named
  pipes. One transport both sides can use natively does not exist, so one side needs a bridge. D-134 put it in the
  daemon; D-135 put it in the window, as `antenna.exe window-bridge` over stdio (WP-5).
- dart:io on Windows: a socket file is a reparse point, so `File(socketPath).existsSync()` is `false`;
  `FileSystemEntity.typeSync()` sees it (Dart's changelog). The window's "is the daemon there" check must use the type
  or just connect.
- The named pipe client PID is not an identity (Project Zero, 2019): through the local SMB server or a mount point
  into the pipe file system it can be chosen, and a pipe handle can be passed on after the opener exits.
- Claude Desktop's MSIX install reads its MCP settings from inside its package folder, not from `%APPDATA%\Claude`.
- `SIO_AF_UNIX_GETPEERPID` reports an output length of 0 on some Windows 10 builds while returning the PID
  (microsoft/WSL#4676): never test the length.
- openssl-src needs a native Perl; in Git Bash the first `perl` on `PATH` is MSYS's.

## 6. Questions for the maintainer

1. **Owner sessions in a terminal (WP-10).** Windows has no terminal identity a same-user process cannot borrow, so the
   CLI would ask for the password for each owner command that needs a session (until Windows Hello, W5). Accept, or
   keep a weaker cache with its risk stated?
2. **Windows Hello and new cryptography in the daemon (WP-26).** Approvals: RSA-2048 signature verification through
   `aws-lc-rs` (already in every build; a new algorithm for owner keys). Unlock: (a) the scheme KeePassXC and Bitwarden
   use (a Windows Hello signature over a stored random challenge, hashed into the key that wraps the slot; it relies on
   deterministic signatures), experimental; or (b) a WebAuthn platform passkey with the PRF extension (a standard
   key derivation in the authenticator; ES256 approvals; Windows 11 25H2 and later only). Both are cryptographic
   decisions for the maintainer (`CONTRIBUTING.md`, security rules).
3. **Signing.** Azure Artifact Signing needs an Azure subscription and an identity validation of the publishing
   organization; whose organization signs, and when (W4)?
4. **Sandbox fallback (WP-20).** If AppContainer cannot carry the agent CLIs, is a one-time administrator setup (a
   sandbox user and a firewall rule, as Codex's elevated mode does) acceptable, or does wake stay off on Windows?
